    06 — Implementation Phases¶

    This document breaks the WASM plugin support into concrete, shippable phases. Each phase delivers usable functionality and can be released independently.

    Phase 1: Foundation — Config Plugins¶

    Goal: Ship the minimum viable WASM plugin support with config plugins as the proving ground.

    Deliverables¶

    1. wazero dependency
    2. Add github.com/tetratelabs/wazero to go.mod.
    3. Verify CI builds pass with CGO_ENABLED=0 across all targets.

    4. Confirm binary size increase is acceptable (~5.5 MB).

    5. Core WASM runtime (pkg/zhiplugin/wasmloader/)

    6. runtime.go — wazero runtime creation, compiled module cache.
    7. memory.go — Shared memory protocol: malloc/free wrappers, host_set_output/host_set_error host functions, string/JSON read/write helpers.
    8. options.go — Option type: WithLogger, WithCapabilities, WithTimeout.

    9. loader.go — LoadConfig() function: compile module, instantiate host functions, instantiate WASI (if needed), instantiate module, return adapter.

    10. Config adapter (pkg/zhiplugin/wasmloader/adapter_config.go)

    11. Struct implementing config.Plugin by calling WASM exports (zhi_config_list, zhi_config_get, zhi_config_set, zhi_config_validate).

    12. JSON serialization/deserialization matching the gRPC layer's convert.go patterns.

    13. Config host functions (pkg/zhiplugin/wasmloader/host_config.go)

    14. zhi_v1 host module with host_set_output, host_set_error, host_log.

    15. ABI version check (zhi_abi_version export).

    16. Discovery changes (internal/core/discovery.go)

    17. PluginFormat type and PluginInfo.Format field.
    18. .wasm file detection in discoverFlat() and discoverSubdirectory().

    19. Native-over-WASM precedence with warning log.

    20. Registry changes (internal/core/registry.go)

    21. launchExternalConfig dispatches to LoadWASMConfig for WASM format.

    22. ProviderInfo.Source shows "wasm" for WASM plugins.

    23. Go PDK — config (pkg/zhiplugin/wasmpdk/)

    24. pdk.go — Core ABI: setOutput, setError, readString, Run.
    25. config.go — ConfigPlugin interface, RegisterConfig, WASM exports via //go:wasmexport.

    26. types.go — Value, TreeReader, ValidationResult.

    27. Example: WASM config plugin

    28. Port the existing examples/zhi-config-pokedex/ to WASM as examples/zhi-config-pokedex-wasm/.
    29. Identical functionality, built with GOOS=wasip1 GOARCH=wasm.

    30. Test that it works interchangeably with the native version.

    31. Tests

    32. Unit tests for the wasmloader package.
    33. Unit tests for the PDK package (standard Go tests, not WASM).
    34. Integration test: compile WASM example → load via wasmloader → exercise all 4 config methods.

    35. Discovery test: mixed native + WASM plugins in a directory.

    36. Documentation

      • Update docs/plugin-development/ with a WASM plugin guide.
      • Update docs/user-guide/workspace-configuration.md with WASM capability syntax.

    What ships¶

    Users can write config plugins in Go, compile to .wasm, drop into ~/.zhi/plugins/, and use them in workspaces. The engine treats them identically to native config plugins.

    Phase 2: Transform Plugins¶

    Goal: Extend WASM support to transform plugins.

    Deliverables¶

    1. Transform adapter (pkg/zhiplugin/wasmloader/adapter_transform.go)
    2. Implements transform.Plugin by calling zhi_transform_before_display, zhi_transform_after_save, zhi_transform_validate_policy.

    3. Handles full-tree JSON serialization (input) and deserialization (output) for the mutable tree pattern.

    4. Transform PDK (pkg/zhiplugin/wasmpdk/transform.go)

    5. TransformPlugin interface, RegisterTransform.

    6. Tree type with List(), Get(), Set(), Delete() for in-WASM tree manipulation.

    7. LoadTransform in wasmloader

    8. Registry integration (launchExternalTransform dispatch).

    9. Example: WASM transform plugin

    10. Simple example (e.g., base64 encode/decode, case transform).

    11. Tests

    12. Integration test: compile → load → before_display → verify tree mutation → after_save → verify.

    What ships¶

    Users can write transform plugins in Go/WASM. Combined with Phase 1, config + transform covers the "data pipeline" portion of zhi without any process spawning.

    Phase 3: Security and Capabilities¶

    Goal: Implement the capability-based security model.

    Deliverables¶

    1. Capability configuration
    2. Parse wasm.capabilities from zhi.yaml workspace config.
    3. Capabilities struct in wasmloader options.

    4. Default capabilities (clock, random: yes; fs, net, env: no).

    5. Filesystem host functions

    6. host_fs_read, host_fs_write, host_fs_list, host_fs_delete, host_fs_mkdir, host_fs_stat.
    7. Path validation: resolve against allowed directories, reject traversal.

    8. FSConfig integration with wazero's WASI module.

    9. HTTP host function

    10. host_http_request with URL allowlisting.

    11. Timeout propagation from Go context.

    12. Environment variable scoping

    13. Only granted env vars passed to module config.

    14. Memory limits

    15. WithMemoryLimitPages on module config.

    16. Execution timeouts

    17. Context deadline propagation for each method call.

    18. PDK host call wrappers

    19. wasmpdk.HostFS.Read(), .Write(), etc.

    20. wasmpdk.HostHTTP.Do().

    21. Audit logging

    22. Log capability usage at DEBUG level.

    23. Log denied capability access at WARN level.

    24. Tests

    25. Test: plugin with no capabilities cannot call fs/net host functions.
    26. Test: plugin with scoped fs access can only read allowed paths.
    27. Test: plugin with net access can only reach allowed hosts.
    28. Test: memory limit enforcement.
    29. Test: timeout enforcement.

    What ships¶

    WASM plugins run in a fully sandboxed environment. Administrators can grant precise capabilities. Denied access is logged and does not crash the plugin.

    Phase 4: Store Plugins¶

    Goal: Enable WASM store plugins using the host functions from Phase 3.

    Deliverables¶

    1. Store adapter (pkg/zhiplugin/wasmloader/adapter_store.go)
    2. Implements all 23 methods of store.Plugin.

    3. Each method maps to a zhi_store_* WASM export.

    4. Store PDK (pkg/zhiplugin/wasmpdk/store.go)

    5. StorePlugin interface (mirrors store.Plugin).
    6. RegisterStore, WASM exports for all 23 methods.

    7. Types: Capabilities, AuthMethod, Credential, PutOptions, Permission, etc.

    8. LoadStore in wasmloader

    9. Registry integration.

    10. Example: WASM in-memory store

    11. Port examples/zhi-store-memory/ to WASM.

    12. Pure in-memory, no host function calls needed.

    13. Example: WASM file-based store

    14. New example that uses host_fs_* functions to persist JSON files.

    15. Demonstrates capability grants in zhi.yaml.

    16. Tests

    17. Full store interface integration test.
    18. Capability-gated filesystem access test.

    What ships¶

    Users can write store plugins in WASM. In-memory stores work with zero capabilities. File-based stores work with scoped filesystem grants. Network-backed stores (e.g., Vault) work with HTTP grants.

    Phase 5: UI Plugins (Stretch Goal)¶

    Goal: Enable WASM UI plugins for non-TTY UIs (HTTP-based).

    Deliverables¶

    1. Controller host functions
    2. All 25 host_ctrl_* host functions from the ABI spec.

    3. Each calls through to the UIController on the host side.

    4. UI adapter (pkg/zhiplugin/wasmloader/adapter_ui.go)

    5. Implements ui.Plugin by calling zhi_ui_run and zhi_ui_capabilities.

    6. Capabilities always returns RequiresTTY: false.

    7. Apply streaming (Option A: polled iteration)

    8. host_ctrl_apply_start, host_ctrl_apply_next, host_ctrl_apply_result host functions.

    9. UI PDK (pkg/zhiplugin/wasmpdk/ui.go)

    10. UIPlugin interface, RegisterUI.

    11. Controller wrapper with methods for all host functions.

    12. HTTP listener host functions (optional)

    13. host_http_listen, host_http_accept, host_http_respond.

    14. Enables WASM plugins to serve HTTP UIs.

    15. Example: WASM HTTP UI

    16. Port or adapt examples/zhi-ui-http/ to WASM.

    17. Tests

    18. Integration test exercising the Controller callback chain.

    What ships¶

    HTTP-based UI plugins can be written as WASM modules. TTY-based UIs remain native-only. This completes WASM support for all four plugin types.

    Phase 6: Distribution and Tooling¶

    Goal: Polish the developer and user experience.

    Deliverables¶

    1. OCI distribution
    2. zhi-plugin.yaml supports format: wasm with os: any, arch: any.
    3. zhi plugin publish handles WASM artifacts.

    4. zhi plugin install detects .wasm and places correctly.

    5. Plugin scaffolding

    6. zhi plugin new --format wasm generates WASM plugin project.

    7. CLI display

    8. zhi plugin list shows format column (native/wasm).

    9. zhi plugin info shows capabilities for WASM plugins.

    10. CI pipeline updates

    11. release-plugins.yml builds WASM examples alongside native.

    12. WASM artifacts published as os: any OCI manifests.

    13. Makefile targets

    14. make build-wasm-examples
    15. make test-wasm (runs WASM integration tests)

    Dependency Summary¶

    Phase Depends On New Dependencies
    1 — github.com/tetratelabs/wazero
    2 Phase 1 None
    3 Phase 1 None
    4 Phase 1, 3 None
    5 Phase 1, 3, 4 None
    6 Phase 1–5 None

    The only new external dependency is wazero, added in Phase 1.

    Risk Assessment¶

    Risk Likelihood Impact Mitigation
    wazero API changes Low (v1.0+ stable) Medium Pin version, update incrementally
    Go wasip1 limitations Medium Medium Test early; fall back to TinyGo for edge cases
    Performance unacceptable for store ops Low Medium Profile early; native plugins remain available
    ABI design needs revision after Phase 1 Medium Low Version the ABI (zhi_v1); Phase 1 is the proving ground
    //go:wasmexport doesn't support needed signatures Low High Test with Go 1.24+ early; use raw WASM exports as fallback
    wazero filesystem sandbox escape Known Low Don't rely on WASI fs; use custom host functions with path validation
    Binary size concerns with Go gc WASM Medium Low TinyGo option available; WASM is still smaller than native

    Success Criteria¶

    Phase 1 is successful if: - A WASM config plugin passes all the same integration tests as its native equivalent. - CI builds pass on all platforms (linux/darwin × amd64/arm64) with the wazero dependency. - The WASM plugin is discoverable and usable without any workspace configuration changes.

    The full feature is successful if: - All four plugin types (config, transform, store, UI) can be implemented as WASM plugins. - WASM plugins are demonstrably more secure than native plugins (capability enforcement, no arbitrary syscalls). - Plugin authors can build and distribute WASM plugins using the PDK and OCI pipeline. - Performance is acceptable for typical plugin workloads (config load/save, transform, store get/put).
